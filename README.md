# Pico W GUD Display

Turn a **Raspberry Pi Pico W** and a small SPI TFT into a **native Linux display
output**. The Pico implements [GUD](https://github.com/torvalds/linux/blob/master/include/drm/gud.h)
(Generic USB Display), a vendor-class USB protocol spoken by the Linux `gud`
driver, so the system sees an ordinary DRM monitor: compositors place windows on
it, it has an EDID, a preferred mode, a backlight and DPMS — no serial-port
framebuffer streaming, no userspace daemon.

Verified end to end with a Pico W (RP2040) and a LCDWIKI **MSP3222/MSP3223**
3.2″ 240×320 IPS panel (ILI9341V) under [niri](https://github.com/YaLTeR/niri),
on Fedora with kernel 6.19. Any compositor that can drive a KMS output should
work the same way.

## How it works

```
compositor ──atomic commit──▶ kernel gud driver ──USB vendor class──▶ Pico
                                                                      │  LZ4 decompress
                                                                      │  XRGB8888 → RGB565
                                                                      ▼  4-wire SPI @ 62.5 MHz
                                                                     panel
```

* Linux sends only the **damaged rectangles** of each frame, LZ4-compressed.
* The firmware decompresses, converts **XRGB8888 → RGB565** (the panel's native
  format) and writes the pixels to the panel over SPI.
* The backlight is a PWM output on the panel's `LED` pin, driven by the
  compositor's brightness property; DPMS off, USB suspend and disconnect turn
  it off.
* EDID is generated by the firmware (name `PicoW-TFT`, 240×320 preferred mode),
  so the output appears with a proper name and physical size.

The GUD protocol implementation is vendored from
[notro/gud-pico](https://github.com/notro/gud-pico) (MIT) with tighter input
validation and a resettable state machine; see `third_party/gud/UPSTREAM.md`.

## Hardware and wiring

| Part | Notes |
| --- | --- |
| Raspberry Pi Pico W | RP2040; Wi-Fi is unused |
| LCDWIKI MSP3222 / MSP3223 | 240×320 IPS, ILI9341V, 4-wire SPI; touch (MSP3223) and the SD slot are unused |

| TFT pin | Pico W GPIO / power | Physical pin |
| --- | --- | --- |
| MISO | GP16 | 21 |
| CS | GP17 | 22 |
| SCK | GP18 | 24 |
| MOSI | GP19 | 25 |
| RS / DC | GP20 | 26 |
| RST | GP21 | 27 |
| LED | GP22 | 29 |
| VCC | VBUS (USB 5 V) | 40 |
| GND | GND | 23 |

Disconnect USB before changing wiring. The `LED` pin drives the module's onboard
backlight transistor, not the LEDs directly. All GPIO signals are 3.3 V; the
module's level shifter tolerates both 3.3 V and 5 V logic. The panel and its
~95 mA backlight are powered from USB. Leave the SD slot empty.

## Performance (measured)

| | Value |
| --- | --- |
| SPI clock | **62.5 MHz** — the RP2040's ceiling, `clk_peri ÷ 4` |
| USB | Full Speed, 12 Mbit/s (the RP2040's maximum) |
| Transfer chunk | 68 full-width rows (65,280 B of XRGB8888) |
| Full-screen repaint | **~60–70 ms** (five chunks) |
| Small damage | one chunk, a few milliseconds |
| Idle | zero USB traffic — updates are damage-driven |

SPI is only ~4 ms of each chunk; the rest is USB round trips, so the transfer
buffer size matters more than the clock at this point. Full-screen changes are
visible as a top-to-bottom fill; text and cursor updates feel immediate.

## Building

All tooling installs into a dedicated **`pico-screen-build` distrobox**; the
host stays untouched. Versions (Debian image digest, Pico SDK 2.3.1, picotool
2.3.1) are pinned in `tooling/versions.env`; sources and build outputs stay in
the project directory.

```sh
bash tooling/setup.sh    # create the distrobox and build toolchain (once)
bash tooling/build.sh    # build firmware, validate UF2 → dist/pico_w_screen.uf2
bash tooling/test.sh     # clang-format check, protocol tests, ASan/UBSan fuzzing
```

## Flashing

Hold **BOOTSEL** while connecting USB, then:

```sh
python3 tooling/flash.py   # mounts RPI-RP2, validates, copies
```

Or drag `dist/pico_w_screen.uf2` onto the **RPI-RP2** drive. On boot the panel
shows red, green, blue, white, black and yellow bars for a few seconds —
visible before USB even enumerates — and Linux replaces it with display content.

## Configuration

Build-time options, all with working defaults:

| Option | Default | Notes |
| --- | --- | --- |
| `SCREEN_ROTATION` | `0` | `0`, `90`, `180`, `270` |
| `SCREEN_SPI_HZ` | `62500000` | Requested clock; the RP2040 divides down. Ladder: 62.5, 31.25, 20.83, 15.625, 12.5, 10.42, 8.93 MHz |
| `SCREEN_BUFFER_SIZE` | `65536` | Caps each USB transfer; 64 KiB = 68 rows |

`bash tooling/build.sh -DSCREEN_ROTATION=90` for landscape.

The ILI9341's specified maximum is 10 MHz; the 62.5 MHz default is a 6.25×
overclock, verified clean on this module and wiring. If the image ever corrupts
(speckles, banding, shifted pixels), step down the ladder.

## Verifying on Linux

The kernel must provide `gud` (`modinfo gud`). After flashing:

```sh
lsusb -d 16d0:10a9      # the device
modetest -M gud -c      # connector, mode, EDID blob
niri msg outputs        # compositor view
```

Expected: a USB device `16d0:10a9`, a DRM connector with mode `240x320`, and an
output named `PicoW-TFT`. EDID rounds the panel size to whole centimetres
(50×70 mm for a 49×65 mm active area) — normal EDID behaviour.

### Diagnostics

Two small tools talk to the device without disturbing the kernel driver
(build them with `bash tooling/probe-host.sh`; they need root for USB access):

```sh
sudo build/probe-host      # GUD descriptor, SPI clock, frame/error counters, raw SPI readback
sudo build/poll-host 6     # frame counter at ~3 kHz, for timing screen updates
```

## Design notes

* **XRGB8888 only, deliberately.** GUD treats a change of framebuffer format as
  a mode change (`old_fb->format != format` ⇒ `mode_changed`), and page flips
  do not carry `ALLOW_MODESET`. The kernel's fbcon console otherwise allocates
  an RGB565 buffer because the device advertises RGB565 (`preferred_depth` 16),
  while compositors render XRGB8888 — so every page flip from one format to the
  other is rejected with `EINVAL`, forever, and the panel stays black while USB
  looks perfectly healthy. Advertising a single format makes fbcon and the
  compositor agree. Do not add RGB565 back without solving this — halving the
  payload is worth doing, and `AGENTS.md` records exactly where the kernel
  performs the conversion and what blocks the switch.
* **Bounded transfers.** The device reports a maximum buffer size, so the kernel
  splits damage into rectangles of at most that size; the firmware never needs a
  full framebuffer (307,200 B) — only two 64 KiB buffers.
* **Blocking SPI.** Each chunk is written synchronously; the resulting per-chunk
  cost is well inside every USB timeout, and it keeps the bring-up path simple.
* **USB ID.** `16d0:10a9` is the GUD display ID the in-kernel driver matches and
  that upstream `gud-pico` uses; it is not ours (the vendor string resolves to
  an unrelated company). Fine for personal use — a distributed product should
  use its own VID/PID, with a driver alias for the kernel.

## Limitations

* **Panel readback does not work on the tested module**: MISO reads constant
  `0x00`, so RDID4 and status registers return zero and the controller ID shows
  as `0x000000`. Display output is write-only and unaffected.
* Touch controller, SD slot and Wi-Fi are not implemented.
* Full Speed USB is the throughput ceiling; 240×320 video is not viable, but UI
  content is comfortable.
* One fixed mode (240×320); rotation is a build-time choice.

## Troubleshooting

* **USB enumerates, panel stays black.** Check the compositor's log for
  page-flip failures with `EINVAL`; that is the framebuffer-format mismatch
  described above. This firmware avoids it by advertising only XRGB8888.
* **A phantom output appears after reflashing.** Reflashing re-enumerates the
  USB device as a new DRM card; a running compositor keeps the old card as a
  dead output that logs errors until the compositor restarts.
* **Corrupted image.** The SPI link has hit its limit — rebuild with a lower
  `SCREEN_SPI_HZ`.
* **Panel dark while USB is connected.** The backlight follows DPMS; check the
  connector's brightness/DPMS properties, or probe `probe-host` for the frame
  counters.
